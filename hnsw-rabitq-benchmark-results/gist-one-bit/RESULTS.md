# GIST-1M 纯 1-bit 对比：Zvec HNSW-RaBitQ vs Elasticsearch 8.18.8 BBQ-HNSW

## 1. 运行环境

| 项 | 值 |
|---|---|
| CPU | Intel Xeon 6982P-C，8 物理核 / 16 逻辑核，单 socket，单 NUMA |
| 绑核 | `0,2,4,6,8,10,12,14`（每物理核一个逻辑 CPU），Zvec 进程、ES client、ES JVM 同一 cpuset |
| 内存 | 61 GiB，swap 关闭 |
| 内核 | 5.10.134-19.2.al8.x86_64 |
| Zvec commit | `30c132a`（pybuild Release，Python 3.11.15） |
| Elasticsearch | 8.18.8 官方镜像，rootless Docker，1 shard / 0 replica / `_source` 关闭，JVM `-Xms4g -Xmx4g` |
| 数据集 | `gist-960-euclidean.hdf5`，1,000,000 × 960 FP32 建库，1,000 query，SHA-256 `8e95831936bf…f026a` |

机器只有 8 物理核（README 基线为 16），因此 build threads 降到 8、搜索线程降到
`1,4,8`。Docker 为 rootless、cgroup driver `none`，无硬内存上限，容器 CPU 由
`taskset` 限制。

## 2. 配置

| 项 | Zvec | Elasticsearch |
|---|---|---|
| 索引 | `HNSW_RABITQ`，`total_bits=1`，`num_clusters=16` | `bbq_hnsw`（1-bit BBQ） |
| 距离 | L2 | `l2_norm` |
| HNSW | `M=16`，`ef_construction=100` | `m=16`，`ef_construction=100` |
| 精排 | 不访问 raw vector | 请求不含 `rescore_vector` |
| 最终段 | `optimize()+flush` | `force_merge(max_num_segments=1)`（1 segment） |

## 5. 固定 Recall 处的对比

两条 Pareto 曲线没有 Recall 重叠区间：ES 的 Recall@10 上限 0.3220（`num_candidates=1000`）
低于 Zvec 的 Recall@10 下限 0.4677（`ef=32`）。因此无法在共同 Recall 点插值，
Zvec 在本实验的整个 Recall–QPS 平面上完全支配 ES：

| 线程 | ES 最高 Recall@10 点 | Zvec 最低 Recall@10 点 | Recall 差 | QPS 差 |
|---:|---|---|---:|---:|
| 1 | 0.3220 @ 167.0 QPS | 0.4677 @ 3545.5 QPS | +0.146 | 21.2× |
| 4 | 0.3220 @ 622.6 QPS | 0.4677 @ 13050.1 QPS | +0.146 | 21.0× |
| 8 | 0.3220 @ 1003.8 QPS | 0.4677 @ 21605.5 QPS | +0.146 | 21.5× |

同参数点（相同 `ef` / `num_candidates` 数值，仅供参考）的 QPS 比值：单线程
5.5×（ef=32）到 1.7×（1000），8 线程 16.1× 到 2.4×。

## 6. 扩展性

| 引擎 | 1→8 线程加速比（参数=32） | 1→8 线程加速比（参数=1000） |
|---|---:|---:|
| Zvec | 6.09× | 8.48× |
| Elasticsearch | 2.07× | 6.01× |

ES 在 8 线程时 QPS 在 1000–1345 附近饱和，几乎与 `num_candidates` 无关，说明瓶颈
不在向量搜索本身（HTTP/协调层、单 shard 搜索线程池）。Zvec 的 QPS 随 `ef` 单调下降，
行为符合纯搜索负载。

## 7. 第二轮：高 Recall 配置（Zvec 7-bit vs ES oversample 调参）

第一轮两条曲线的 Recall 区间不重叠，无法做等 Recall 比较。第二轮补充：

- Zvec `total_bits=7`（重建索引，work dir `../gist-seven-bit`）
- ES 复用同一个 `bbq_hnsw` 索引，只改查询：`rescore_vector.oversample` = 2 / 3 / 5，
  并把 `num_candidates` 扫描范围扩到 2000（`oversample=5` 时 32 不满足
  `num_candidates ≥ k×oversample`，故从 64 起）

| 线程 | Zvec 1-bit QPS | ES best QPS | Zvec/ES |
|---:|---:|---:|---:|

把 `ef` 推到 1000 更划算；正确做法是这一 Recall 区间用 Zvec 7-bit
（1 线程 2176 QPS @0.60），而不是 1-bit 曲线的尾部。

## 8. 结论与限制

- 纯 1-bit 无精排口径：Zvec 完全支配 ES（ES Recall@10 上限 0.322 < Zvec 下限 0.468），
  同时构建快 2.9×、存储小 1.23×。
- ES 调参后（`rescore_vector` oversample 2/3/5 + `num_candidates` 到 2000）可以覆盖
  0.47–0.965 的 Recall 区间，能与 Zvec 做等 Recall 比较。此时 Zvec 7-bit 在
  Recall@10 0.60–0.95 全区间 QPS 领先 **3.9×–12.6×**，领先幅度随并发升高而扩大。
- Zvec 的曲线形状是"提高量化精度"（1-bit→7-bit）；ES 的是"用原向量精排补偿 1-bit"。
  在本数据集上，前者在同 Recall 下明显更省算力；后者的优势是 Recall 天花板更高
  （0.965 vs 0.9497），因为精排最终用的是精确距离。
- ES 在 8 线程处 QPS 饱和（无精排时 ~1000–1345，几乎与 `num_candidates` 无关），
  说明其瓶颈部分来自 HTTP/协调层与单 shard 搜索线程池，而非向量比较本身；
  开了精排后 QPS 与 `num_candidates` 才重新强相关。
- 口径限制：两者量化/距离估计/HNSW 实现不同，非同算法 microbenchmark；ES QPS 含
  宿主机 HTTP 往返，Zvec 为进程内调用。
- 仍未做：每引擎 3 次构建取中位数、`/usr/bin/time -v` 峰值 RSS 与 `docker stats`
  容器峰值内存、16 线程点（本机仅 8 物理核）、Zvec 中间档 `total_bits`（2/4）。
